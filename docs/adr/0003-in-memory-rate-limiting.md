# ADR-0003: レート制限は、プロセス内メモリの固定窓で実装する

- 状態: 採用（2026-09）、範囲を拡大（2026-10）
- 関連: `src/lib/security/rate-limit.ts`、`oauth-rate-limit.ts`、`client-ip.ts`

## 背景

お問い合わせフォームはメールを送るため、連打されると迷惑メールの踏み台や、送信上限の消費につながる。管理画面のログイン処理も、総当たりの対象になりうる。ただし、このサイトは小規模で、外部のデータストアを持たない。

## 決定

- クライアントの識別は、`x-forwarded-for` の先頭、なければ `x-real-ip`（`lib/security/client-ip.ts`）。取れない場合は共通の `unknown`。
- 固定窓のカウンタを `Map` に持つ（`checkRateLimit(key, limit, windowMs)`）。
  - お問い合わせ: IP ごとに 10 分で 5 回。
  - 管理画面の OAuth: IP ごとに 10 分で 10 回。キーに接頭辞を付け、お問い合わせの枠と混ぜない。
- 超過すると 429 を返す。画面側は、送信失敗として表示する。

## 結果

- 良い: 依存が増えず、実装が数十行で、テストしやすい。通常の利用（数回の送信）は妨げない。
- 悪い: サーバーレス環境では、インスタンスごとにカウンタが別で、コールドスタートでも消える。複数のインスタンスに分散した攻撃は、完全には止められない。`x-forwarded-for` は、信頼できるプロキシ（Vercel）の背後でのみ正しい。
- 補完: 本文の大きさの上限（16KB）、honeypot、入力の検証、メール側の送信上限で、多重に守る。

## 検討した代替案

- Redis / Upstash / Vercel KV で共有カウンタを持つ: 正確だが、外部サービスの契約と設定が増える。現在の規模には過剰。
- CAPTCHA: 利用者の負担が増える。honeypot とレート制限で、現状は足りている。

## 見直す条件

実際に濫用が観測された場合、またはアクセスが増えた場合は、共有ストアのレート制限（Upstash など）に移す。`checkRateLimit` の呼び出し側は変えずに、実装だけ差し替えられる。
